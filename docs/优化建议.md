# 桌面宠物项目 · 优化项清单

**文档性质**：技术交接说明
**适用范围**：`aicomputerpet` 桌面宠物项目全部源码与模型资产
**数据来源**：本机实测（2026-09），全部结论附有可复现的验证入口
**阅读约定**：本文档仅陈述现状、证据与影响范围，不包含实现方案

## 0. 文档说明

本项目由前一版 AI 模型迭代完成。本文档面向后续维护者，目标有二：

1. 列出经核实、可以修改或优化的具体位置；
2. 标注已经排除的排查方向，避免重复投入。

每一条目采用统一结构：**类型 / 位置 / 现象 / 证据 / 影响**。

类型分为三类：

| 类型 | 含义 |
| --- | --- |
| **缺陷** | 与预期行为不符，已确认 |
| **优化项** | 行为正确，但存在改进空间 |
| **约束** | 由模型或依赖决定，改动时必须保持兼容 |

## 2. 用户反馈项

本节各条由用户直接提出，按可验证程度排序。

### 2.1 模型参数调节无效

**类型**：缺陷（已确认）

**位置**：`src/renderer/pet.js:226 / :248 / :268`，`src/renderer/ui/settings/panel.js` 的 `case 'param'` 分支

**现象**：在「设置 → 模型参数」中修改任一参数的上下限或模式，模型无任何变化。

**证据**：

```js
// pet.js 中三处覆盖逻辑的首行
const mp = this.settings?.modelParams
if (!mp?.enabled) return          // ← 总开关关闭时全部直接返回
```

`modelParams.enabled` 的默认值为 `false`，而面板中每个参数的模式选择器与数值控件
**只受 `locked` 约束，不受总开关约束**：

```js
const modeSel = el('select', { disabled: locked, ... })   // 未检查 enabled
```

即：总开关位于「总览」分组，单项控件位于其余六个分组，
**在总开关关闭时，单项控件外观完全正常且可交互，但写入的值不会被应用，且界面无任何提示**。

**影响**：该功能在默认配置下等同于不可用。用户需先发现并开启总开关，否则所有操作静默失效。

---

### 2.2 参数调节缺少生效反馈

**类型**：优化项

**位置**：`src/renderer/ui/settings/panel.js`

**现象**：调节参数后无法判断是否已应用。

**证据**：

- 总开关关闭时无禁用态、无提示（见 2.1）
- 面板虽有「已修改」标记（左侧蓝色边条），但该标记只表示**配置值与默认值不同**，不表示**该配置已被运行时采纳**
- 实时曲线仅在「模型参数」页且采样开启时绘制；曲线显示的是引擎输出值，不反映覆盖是否生效

**影响**：配置状态与运行时状态之间缺少可观测的对应关系。

### 2.3 嘴部视觉不明显

**类型**：缺陷（模型侧）

**位置**：模型里的嘴部 art mesh（`ArtMeshMouth` / `ArtMeshMouth_lip_0` / `ArtMeshMouth_lip_1`）

**现象**：模型无可见嘴部。

**已排除的排查方向**（无需重复验证）：

| 检查项 | 结果 |
| --- | --- |
| 网格存在 | `ArtMeshMouth` 75 顶点 / 288 索引；上下唇描边各 98 顶点 / 264 索引 |
| 渲染顺序 | 17，位于 `ArtMeshFace`(15) 之后，处于上层 |
| 不透明度 / 可见性 / 遮罩 | 1 / true / masks=0，混合模式 0（正常） |
| 几何位置 | 位于鼻子正下方，宽度约为面部的 10% |
| 贴图内容 | UV 区域存在像素（v 翻转后采样，31% 不透明，高于鼻子区域） |
| 对 `ParamMouthOpenY` 的响应 | 存在但幅度极小：0→1 时包围盒面积由 2.26e-5 增至 5.86e-5 |
| 实际渲染结果 | 8 倍放大后，任意参数取值下均无可见嘴部 |

**测量方法可信度**：以 `ParamAngleX` 为对照，设为 45° 时面部网格顶点确实发生位移
（`[-0.035, 0.418, …]` → `[-0.023, 0.421, …]`），证明顶点探针读取的是实时形变数据。

**成因线索**：模型工程文件（`*.psd2live.json`）的 `warnings` 字段：

> CMO3：未保留原始 PSD 源图编辑链；已从 1 页贴图重建可编辑图层（模型/Rig 数据仍保留）

即该模型由单页贴图重建导出。嘴部关键形算法位于 `RigBuilder.kt:1702 mouthWholePoint()`。

**附带上报**：`coreModel.getDrawableVertices(i)` 返回的坐标量级异常
（面部包围盒约 `0.1 × 0.1`，而画布为 1024²），与 `getDrawableBounds` 的口径不一致。

**用户补充**：允许对模型进行适度修改。

### 2.4 眼睛分层效果不理想

**类型**：优化项（模型侧）

**位置**：`ArtMeshEyewhiteL/R`、`ArtMeshIridesL/R`、`ArtMeshEyelashL/R`、`ArtMeshEyebrowL/R`

**现象**：眼部各图层的叠加效果不佳。

**证据**：眼部网格密度显著低于其余部位——

| 网格 | 顶点数 | 索引数 | 遮罩 |
| --- | --- | --- | --- |
| `ArtMeshEyewhiteL` | **9** | 24 | 无 |
| `ArtMeshIridesL` | **9** | 24 | 有（1 个） |
| `ArtMeshEyebrowL` | 12 | 30 | 无 |
| `ArtMeshEyelashL` | 25 | 69 | 无 |
| 对照 `ArtMeshFace` | 72 | 339 | 无 |
| 对照 `ArtMeshBottomwear` | 79 | 279 | 无 |
| 对照 `ArtMeshLegwearL` | 101 | 342 | 无 |

9 顶点 / 24 索引相当于一个 8 三角形的基础网格。`ParamEyeLOpen` 由 1 降至 0 的闭眼形变
仅由该密度承担，形变精度受限。

眼部渲染顺序（数值小者先绘制）：

```
20 ArtMeshEyebrowR → 21 ArtMeshEyewhiteR → 22 ArtMeshEyewhiteL
→ 23 ArtMeshEyebrowL → 24 ArtMeshIridesR → 25 ArtMeshIridesL
→ 26 ArtMeshEyelashL → 27 ArtMeshEyelashR
```

左右眉分别插入在左右眼白之间，非成对连续。瞳孔具备遮罩，眼白不具备。

## 3. 模型与渲染

### A1. 库内置「示例呼吸」与 psd2live 绑定无关

**类型**：缺陷（已规避）

**位置**：`src/renderer/live2d/stage.js` 的 `load()`

**现象**：pixi-live2d-display 在构造模型时注入一组通用呼吸参数：

| 参数 | 幅度 |
| --- | --- |
| `ParamAngleX` | **±15°** |
| `ParamAngleY` | ±8° |
| `ParamAngleZ` | ±10° |
| `ParamBodyAngleX` | ±4° |
| `ParamBreath` | 0↔1 |

psd2live 规范中呼吸仅通过 `ParamBreath` 表达（胸腔高斯膨胀），
头身摇摆属于 Idle 动作曲线。该注入组与模型绑定无关。

**现有处理**：将 `internalModel.breath` 置为 `null`，改由 `Pet` 自行写入 `ParamBreath`。
该处理直接改写依赖库的内部字段，依赖库版本升级时假设可能失效。

**实测影响**（处理前后）：

```
待机头部摇摆    -5.9 ~ +5.8°   →   -2.1 ~ +1.9°    （Idle 曲线为 ±2°）
Shake 动作摆幅   38.5°          →    39.9°          （曲线为 40°）
```

---

### A2. Cubism 每帧管线契约未在代码中固化

**类型**：优化项

**位置**：`src/renderer/pet.js`（`_applyEarlyParameters` / `_applyParameters`）、`stage.js`

**现象**：依赖库的实际执行顺序为

```
motion → saveParameters → expression → eyeBlink → focus → breath → physics
       → [beforeModelUpdate 钩子] → model.update() → loadParameters()
```

其中 `loadParameters()` 每帧将参数回滚至 `saveParameters()` 的快照。
由此衍生三项必须持续维持的性质：

1. 角度参数只能**叠加**写入（`addParamClamped`）；直接赋值会抹平动作曲线
2. 眨眼必须写在 physics 步骤**之前**，否则 `PhysicsEyeJelly` 读不到该值
3. 眼球开合必须**相乘**而非赋值，否则丢失动作曲线中 0.75 的眯眼量

上述三项目前由自测断言锁定，但代码层面无强制机制。

**附带**：`pet.js:405` 调用 `_applyManual(core, 'rest')`，
而函数体仅判断 `phase === 'early'`（`pet.js:255`）。
逻辑上依赖「非 early 即全量」生效，命名与实际语义不一致。

---

### A3. 手动覆盖分两阶段写入

**类型**：优化项

**位置**：`src/renderer/pet.js` `_applyManual(core, phase)`

**现象**：`early` 阶段仅写入眼睛参数的绝对值，`final` 阶段写入全部。
目的是使果冻眼物理读取到眼睛值，同时避免 `offset` 模式被重复叠加。

**影响**：`offset` 模式对眼睛参数而言，物理步骤无法感知，此不对称性未在代码或文档中说明。

---

### A4. 视线控制器常量固定，漂移为确定性正弦

**类型**：优化项

**位置**：`src/renderer/live2d/gaze.js`（45 处硬编码数值）

**现象**：

- 漂移由固定正弦叠加生成，每次运行完全一致，长时间观察呈现明显规律性
- 视线至参数的映射（`headAmount` / `eyeAmount` / `eyeMax` / falloff 曲线）均为固定常量
- 视线与动作曲线共用 `ParamAngleX/Y`，以叠加方式共存，幅度上限由模型参数范围硬性截断

## 4. 运行时参数

### B1. 自动模式上下限采用事后钳制

**类型**：优化项

**位置**：`src/renderer/pet.js` `_applyAutoClamps()`

**现象**：在完整管线执行完毕后，读取结果并再次截断。由此产生：

- 截断作用于**最终值**，无法区分来源（动作曲线 / 视线 / 情绪）
- 被截断的部分不反馈至上游（例如视线仍按未截断的目标持续输出）
- 与 `fixed` 模式属于两条不同代码路径（后者位于 `_applyManual` 内）

---

### B2. 实时曲线的采样与显示绑定渲染帧率

**类型**：优化项

**位置**：`src/renderer/pet.js` `_trace` / `_traceBuffers`（`TRACE_SAMPLES = 120`）、
`src/renderer/ui/settings/panel.js` `_startCurveLoop()`

**现象**：

- 采样发生在 `_applyParameters` 内，频率等于渲染帧率，无时间轴
- 仅在「模型参数」页激活，切换页面即清空缓冲
- 曲线画布固定为 210×30，值域取模型上下限，无自适应缩放
- 不支持导出、暂停与游标读数

---

### B3. 模型参数取值缺少校验

**类型**：优化项

**位置**：`shared/defaults.json` → `modelParams.items`（自由映射）

**现象**：每项结构为 `{ mode, value, min, max }`，但：

- `mode` 取非法值时，会落入「非 auto」分支被静默处理
- `value` / `min` / `max` 超出模型范围时，仅依赖写入端的截断，越界配置不产生错误提示
- `pruneToSchema` 将 `{}` 视为自由映射，故该结构不受 schema 约束

## 5. 设置系统

### C1. 配置存储的合并语义存在陷阱

**类型**：缺陷（已修复，但机制仍在）

**位置**：`src/main/lib/store.cjs`

**现象**：深度合并**无法删除键**。曾导致「解锁」操作永久失效
（`patch({ locks: {} })` 为空操作）。

**现有处理**：使用 `REPLACE_KEYS = new Set(['locks'])` 特例处理，并以 `null` 表示删除。

**影响**：任何新增的「按删除方式编辑的映射」都会遇到同一问题，且不会产生任何提示。

---

### C2. 设置面板为单文件 1,376 行 / 11 个字段类型分支

**类型**：优化项

**位置**：`src/renderer/ui/settings/panel.js`

**现象**：全部字段类型（`switch (f.type)`）集中于同一方法内。
该文件同时承担导航树、搜索、锁定、预设、动态选项加载、曲线渲染与结果回显，共七项职责。
schema 声明 141 个字段。

---

### C3. 部分设置由渲染进程直接写入

**类型**：优化项

**位置**：`src/renderer/ui/settings/panel.js` `_scanGptsovits()` / `_startGptsovits()`

**现象**：面板自行探测安装目录、构造 `voice.gptsovits.*` 补丁并写回配置。
「探测 → 解释 → 写配置」该逻辑在**三处**各存在一份近似实现：

- `panel.js` `_scanGptsovits()`
- `src/renderer/main.js` `testGptsovits()`
- `src/main/main.cjs` 启动时的自动配置

三处的模式推断与语言推断规则已出现细微差异。

---

### C4. 语言能力判断依赖静态表

**类型**：优化项

**位置**：`src/main/lib/tts.cjs` `providerSupportsLanguage()`

**现象**：按引擎硬编码语言集合，「引擎实际能力」与「表中声明」之间为人工维护的映射。

**已修复的实例**：GPT-SoVITS 曾以 `gptsovits.textLang === 目标语言` 判定能力，
导致中文台词被判为「不支持」，从而被排到降级链末尾。
该字段本意仅为「朗读语言」，与「参考音频语言」是两个独立参数。
现改为依据模型的多语言集合判断。

**同类结构**：`gaze`、`emotion`、`providerSupportsLanguage` 均为静态表，
新增引擎或语言时需在多处同步修改（参见 C3）。

## 6. 语音

### D1. 音调（声线）实现依赖各引擎的 rate 参数

**类型**：约束

**位置**：`src/main/lib/tts.cjs`（历史实现另见已删除的 `sapi.cjs`）

**现象**：实现方式为「令引擎放慢合成 → 播放时以 `playbackRate` 加速 +
`preservesPitch = false`」。由此：

- 仅适用于提供 rate 参数的引擎
- 各引擎可用区间不同，由逐引擎的截断常量维持
- 语速补偿后仍存在约 **8.3%** 偏差

> 历史记录：已删除的 Windows SAPI 引擎在 **+20% 处饱和**、负向至 −45% 近似线性 ——
> 这正是当初需要「逐引擎截断常量」的原因。

---

### D2. GPT-SoVITS 服务端存在偶发 500

**类型**：缺陷（外部依赖）

**位置**：`src/main/lib/gptsovits.cjs`

**现象**：实测原始错误信息为
`GPT-SoVITS /tts 失败 HTTP 500: Internal Server Error`。
与文本内容相关、不可预测，同一句重试通常成功。

**现有处理**：客户端重试一次，失败后进入递增退避冷却（20s / 1min / 5min / 30min）。

**附带**：服务健康状态仅在启动时探测，运行期无持续监控；服务中途退出时，
需等到下一次合成请求才能发现。

---

### D3. 参考音频文稿依赖同名 `.txt` 约定

**类型**：优化项

**位置**：`src/main/lib/gptsovits-scan.cjs`

**现象**：`foo.wav` 与 `foo.txt` 自动配对为参考音频与文稿，语言按文稿字符集推断
（含假名判定为 `ja`，其余判定为 `zh`）。

该约定仅记录于 `refs/README.md`，代码与界面均未体现；
音频缺少同名 txt 时，仅在扫描结果中输出一行提示。

---

### D4. 口型包络常量为人工调定

**类型**：优化项

**位置**：`src/renderer/features/voice.js`

**现象**：采用峰值跟随归一化与快起慢落包络，涉及常量为：
`0.012`（噪声门）、`1.6`（增益）、`0.75`（幂次）、`2.1`（放大）、
`0.994`（峰值衰减）、`0.22`（峰值下限）、`0.06`（闭合阈值）、`0.6 / 0.22`（起落系数）。

上述数值由听感确定，未提供可调入口。

---

### D5. 语音引擎失败记录仅保留最后一次

**类型**：优化项

**位置**：`src/main/main.cjs` `voiceFailures`

**现象**：存储结构为每引擎一条 `{ at, count, error }`，无历史序列，
无法回溯「特定时间窗内的失败次数与原因分布」。

### D6. GPT-SoVITS 服务端按 GBK 处理文本，无 GBK 编码的字符会让整条请求失败

**类型**：缺陷（外部依赖，已在客户端规避）

**位置**：`src/main/lib/gptsovits.cjs` `toGbkSafe()`

**现象**：服务端在 Windows 上以 GBK 处理文本，凡是没有 GBK 编码的字符，
整条 `/tts` 请求都会以 400/500 失败（服务端报 `'gbk' codec can't encode character …`），
与语言无关 —— 中文台词里出现同样的字符一样失败。实测：

| 结果 | 字符 |
| --- | --- |
| 失败 | `・`(U+30FB) `♪`(U+266A) `♥`(U+2665) `✓`(U+2713) `©`(U+00A9) `〜`(U+301C)、全部 emoji 与星平面字符 |
| 正常 | `★`(U+2605) `→`(U+2192) `①`(U+2460) `℃`(U+2103) `！`(U+FF01) `…`(U+2026) `～`(U+FF5E) |

与 Python 的 `gbk` 编解码器逐字符对照，**「有没有 GBK 编码」与实际成败 100% 吻合**；
仅 U+2000–U+2BFF 一个区段就有 2783 个不可编码字符。

**现有处理**：客户端在发请求前，用 `TextDecoder('gbk')` 反向枚举出的 23939 字编码表过滤，
把编码不了的字符换成空格并合并连续空白；界面与聊天记录里的原文不受影响。
运行时不带 GBK 支持时（`TextDecoder` 抛错）原样放行，不阻塞语音。

### D7. 权重模式下服务端仍要求参考音频

**类型**：缺陷（外部依赖）

**位置**：`src/main/lib/gptsovits.cjs` `synthesize()`

**现象**：切到「常驻模型」模式后仍然必须带上 `ref_audio_path` / `prompt_text`，
否则服务端返回 HTTP 500。文档曾写「这时不再需要参考音频」，实测不成立，已更正。

**现有处理**：`useWeights` 分支在 `refAudio` 存在时照常发送参考字段；
「自动检测」也会一并填写参考音频与文稿，所以默认路径不会踩到。

### E2. 测试对合成输入的依赖

**类型**：优化项

**现象**：

- `sendInputEvent` 注入的鼠标坐标在本机发生畸变（发送 1960 实测到达 750；发送 120 实测到达 276）。
  视线断言因此改为直接调用接口设置注视目标；DOM 至视线通路的覆盖仅由抚摸测试承担
- 动作断言依赖「先 `stopAllMotions()` 再静置 500ms」，否则上一次动作的淡出会污染采样
- 半数断言需 `--selftest-api` 并依赖 `scripts/mock-api.cjs`
- **断言期望值不得由实时采样推导**。参数上下限断言原以「采样值 × 0.4 / + 5」构造限值，
  而视线在采样后仍持续移动，限值随即失效（实测：采样为 −5.42，限值 −0.42，
  但随后引擎值升至 +22.56，下限本就不应生效）。
  现改为取模型全量程之外的固定限值（−40 / +40，视线实际仅能达到约 ±14°），
  使断言与实时状态解耦。此类依赖在单次运行中可能通过，跨运行不稳定。

## 12. 缺陷分布特征

本项目全部代码由前一版 AI 模型（DeepSeek V4 Flash）编写。经本轮排查，
已确认缺陷集中在以下类别，可作为后续复查的重点方向：

| 类别 | 本项目实例 | 位置 |
| --- | --- | --- |
| **静默失效**：条件不满足时直接返回，界面无任何提示 | 模型参数总开关 | 2.1 |
| **隐式契约**：依赖文档未记载的调用顺序或内部状态 | Cubism 每帧管线、双阶段写入 | A2 / A3 |
| **逻辑重复**：同一规则在多处实现并逐渐分叉 | GPT-SoVITS 探测与配置推断 | C3 |
| **合并语义误判**：以深合并实现「删除」 | 配置锁 | C1 |
| **静态表**：能力/映射靠人工维护，与实际状态脱节 | 语言能力判断 | C4 |
| **命名与语义不符**：参数名与实际分支逻辑不一致 | `_applyManual(core, 'rest')` | A2 |
| **常量集中缺乏入口**：关键系数散落且不可调 | 口型包络、视线映射 | A4 / D4 |
